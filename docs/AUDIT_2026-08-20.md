### M6 — the squeeze walk-forward gate produces zero folds (corrected diagnosis)
The outcome is real: `runs/squeeze_validation/summary.json` train/oos are entirely
`n:0` / `None`. My first diagnosis of the *mechanism* was wrong and is corrected here.

NOT the cause: `label_horizon=5` does not select the scored column —
`summarize_split(..., fwd_col="fwd_1d")` (`research/squeeze_flow_eval.py:360`) hardcodes
`fwd_1d` and `evaluate_train_oos` never overrides it; `fit_fire_threshold` is called with

NOT the cause: the `except Exception` at `research/squeeze_validation.py:400-401` never
fired. The code is honest — `research/squeeze_flow_eval.py:412-421` returns an explicit
`{"n_folds": 0, "note": "not_enough_dates_for_walk_forward"}` and that note IS in the
saved summary.

ACTUAL cause — date starvation by arithmetic. `research/squeeze_validation.py:378` filters
`scored = panel[panel["error"].isna()]` first; two of the ten asof dates (2026-08-07,
2026-08-09) had exactly one row each and it errored, so `scored["asof"].nunique() == 8`.
Geometry then needs `initial_train(2) + label_horizon(5) + embargo(1) + validation(2) = 10`
against 8 available. Main loop fails; the partial-final fallback needs `remaining >= 1` but
`remaining = 0`. Zero folds. Had those 2 dates survived, one thin fold would have formed —
the configuration sits on a knife's edge.

Real defect: `research/squeeze_validation.py:390-391` derives the split sizes as
`nunique()//3` with no floor check that the geometry can yield even one fold.
Related MINOR: `label_horizon` is threaded into geometry but not into scoring.

## Empirical finding — the squeeze score has no demonstrated edge
The *math* is sound (audited term-by-term: GEX = OI·Γ·100·S²·0.01 with correct call+/put−

  but zero evidence of *positive* edge.
- Score's own top-minus-bottom-quartile return: **−0.28%** (1d), **−1.26%** (3d).
- **The one statistically significant result contradicts the premise**: amplification
  `rank_ic_sr_vs_abs_ret` = **−0.239, t = −2.45, p < 0.05**. Mean |return| for HIGH

data's own caveat that OI is "often single date; assumed sticky."

## Added after first-hand testing against real data (2026-08-20)

### M8 — RETRACTED. The absorption gate is correctly calibrated; I was wrong.
I originally reported that `imbalance_min = 0.3` sat "above its own data's 90th
percentile" and that the board was therefore effectively dead. **That conclusion was
wrong**, and the error was mine: I sampled a single cross-section — the last readout of
each of 59 symbols — and generalised from n=59 to a claim about the threshold itself.

Re-measured over the FULL local history instead (independently reproduced):
```
mature (non-warming) readouts : 296,937
|imbalance| >= 0.30           :  19,369 = 6.52%
vol_ratio   >= 1.50           :  25,852 = 8.71%
signal fires (all gates)      :   1,492 = 0.50%
P(zero hits in one 59-symbol snapshot) = 0.743
```
A 0.50% joint rate is roughly one genuine absorption print per symbol per ~6 weeks of
hourly bars — a rare-but-real event, which is what an absorption detector *should* be.
Observing zero hits in one snapshot has a **74% probability** under that rate. My p90
figure was a property of that one snapshot, not of the estimator.

Correctly lowering the thresholds to "make signals appear" would have been curve-fitting
to 59 points. It was not done.

What WAS real in the original finding: an empty board was **inexplicable**. An operator
could not distinguish "rare event, none right now" from "this surface is broken" — which
is very likely what "the absorption map is broken" actually meant. That is now fixed by a
`gate_summary` on the scan payload (per-gate pass counts + the observed imbalance and
vol_ratio distribution) and a per-row `imbalance_threshold`, so the gate is visible rather
than silent.

Additionally, an opt-in distribution-relative gate was added
(`AbsorptionConfig.imbalance_percentile`, default 0.0 = off, so no existing caller
changes behaviour). It can only ever RELAX the threshold, never tighten it, and is floored
at `0.5 * imbalance_min` so a quiet symbol cannot trip on noise.
`build_absorption_scan` now defaults to `CLV_PROXY_SCAN_CONFIG` (percentile 0.85) because
that path always feeds the CLV proxy — an exact selection, not a guess.
Measured effect on the real 59-symbol universe: directional reads **3/59 -> 12/59**,
signals **0/59 -> 1/59** (CAT, `sell_absorption`, score -0.8194).

### The trap this uncovered: CI would have failed even WITH a `pytest tests` step
`pytest.ini` had `pythonpath = .`, but the suite writes absolute imports
(`from edge.daily_plays.absorption import ...`), which need the checkout's PARENT on
sys.path. It only ever worked locally by accident. Verified first-hand:
```
tests/__pycache__/__init__.cpython-310.pyc   exists (152B)
tests/__init__.py                            does NOT exist in source
git ls-files tests/__init__.py               returns nothing (never tracked)
```
CPython treats a directory holding only compiled bytecode as an importable package, so
`tests` resolved as a package on this machine and would not in a fresh checkout — 87 files
failed with `ModuleNotFoundError: No module named 'edge'` in a clean copy.
Fixed by `pythonpath = . ..` plus a `path: edge` checkout and `working-directory: edge`.
